# Notes while reading recording-plan.md (raw, to be consolidated into review.md)

## Candidate findings (plan)

1. BUILD STRATEGY. Phases 1-12 migrate in place; phase 1 (compile) lands before phase 2 (memory) and 3 (recording/channels), so phase 1's `compile!` must emit into today's vulkan/graph.jl recording and today's memory. That is an adapter deleted two phases later, which "Forbidden moves" forbids ("a compatibility shim", "keeping an old path next to its replacement"). Every phase repeats this. With 53k lines of old code and a ~10k target, in-place migration maximises contact with the old patterns (the "black hole"). Option: fresh core + fresh backends written against the suite, old tree moved aside and consulted only for driver facts, consumers switch once the suite is green. Decide after the src audits report the duplication numbers.
2. HOST NODES multiply the ordering state space: stages, per-stage inbox, arena parts held across host functions with id-ordered holds, mid-run stale changes left pending with host-waiting submitters, throw-from-inside-a-run cycle rule, no fairness. plan 543-706. Ask: is a simpler rule possible (a host node = a cut; stage k+1 behaves exactly as "the next run"; the only extra rule is that arena tenancy spans the stages)?
3. CAPABILITIES / KERNEL PORTABILITY are not modelled. `caps(dev)` lists roofline, sparse, display, timeout, transfer queue, inline-store limit (plan 1385). Nothing about: cooperative matrices (shapes, types), subgroup size, fp16/bf16 arithmetic, Float64, 64-bit atomics, memory ordering (Lava strips acquire/release), ray query in compute vs RT pipeline, mesh shaders. The user's goal "coop matrix extensions should not be handled by the user" needs a capability type the selection table and the kernel compiler dispatch on. Check api.md for a `caps` contract.
4. SELECTION TABLE: "measurement fills the table per device; an unmeasured entry uses core's cost estimate" (plan 283-302). When does measurement run, where is it stored, how is it invalidated, how is it tested? No phase adds it; phase 6 only moves the Vulkan GEMM selection. A design hole for the "state of the art speed" goal.
5. NOUN OVERLOAD: graph / plan / stage / segment / part / piece / group, and "part" means both a segment's recording and an arena part. Rename arena parts.
6. Open decision 10 (repeat! recorded per iteration vs submitted per iteration) is already decided by the mechanism text (loop head zeroes counts; unrolled launches). Close it.
7. Metal open question 2 (per-draw state outside an indirect render command) is closed by the plan's own scene-rectangle rule: viewport/scissor are per pass, applied once by the pass; pieces set no state the ICB cannot hold. Close it, and it removes the "emitted directly in the run's encoder" walk, which would violate rule 1.
8. Open decision 3 (TLAS/textures by address+table vs descriptors): bindless (device address + device-wide tables) is the only form uniform across Vulkan, Metal (resource IDs), CUDA/HIP (texture objects). Recommend closing as bindless now; the suite's tlas.jl/textures.jl already assume it (verify).
9. Phase 0 lists ~22 `test_*.jl` files by name; the executable spec is `test/suite/areas/*.jl` (42 areas) and the ledger P0.T1-T14 lists the `test_*.jl` names. Decide which is the spec and make plan, ledger and suite agree.
10. "`Mantle.refit!` is the acceleration-structure refit; the transient/plan `refit!` has another name" (plan ~1103): the other name is not given.
11. `src/host/` and `HostDevice` are referenced for deletion (phase 8) but src/ has no host/ directory now; Project.toml's comment claims `src/host/host.jl` exists. Stale.
12. Readback vs Unified memory from the user's side: `unified = true` is documented; how a user creates an output "in Readback memory" (plan 912) is not. Check api.md 2.2.
13. Eager = one submission per launch (plan 873-925). Deliberate; consumers that run many small eager ops (GPUArrays generic broadcast chains) pay a submit each. Fine if consumers use graphs for hot paths; check consumer audit for eager-heavy code.
14. Rule 5 says the device registry is the one process-level state; the plan also has device-wide texture/sampler tables, the cell arena, per-device selection tables, kernels at CodeInstances. These are per device (owned by the device object), consistent, but api.md's allowlist of globals must list only the registry.
15. The `Kernel` type's `devices::Vector{DeviceKernel{N}}` searched by identity: fine for a handful of devices.
16. "Each array owns a cell" + "a transient that is not resizable has no cell": a view of a transient? Views share the parent's state; a transient view's slots are static offsets. OK.
17. `MantleArray(location(a), …) do p … end` (plan 121): a do-block constructor for temporaries inside operations. Odd shape: the do-block is the body that uses the temporary; check examples.jl/api.md for the actual form.
18. Windows: "A graph presents to at most one window" + "one graph presents to a window": an editor with two windows (preview + main) needs two frame graphs sharing device arrays. Consistent but the editor_patterns suite should cover two windows.
19. Phase 11 mentions Paperhawk (external repo) and PPOCRRunner/UVDocRunner `Mantle.storage` calls: consumer-specific; fine in the ledger, check they are there.
20. "Definition of done" requires an independent review per phase and a measured baseline per phase: 12 phases x (review + baseline). With a fresh-write strategy there would be one review per area instead.

### Design findings (need a ruling; each with recommendation)
D1. LOCKS. Twelve lock kinds (graph semaphore, arena condition, window, plan sync, SyncState per resource, channel, pool, inbox, table, kernel, registry, runend) and nine optimistic retry sites (lockstage, lockresources, lockexpanded, register!, submitwith!, run!, bindunmapped!, acquireimage!, restoresteps) exist because bookkeeping locks are fine-grained and must be taken in id order from snapshots. The plan already guarantees no host wait under any of them. Recommendation: ONE bookkeeping lock per device (held for microseconds: compute waits, record accesses, take pending changes, update namers/readers/members/inboxes, claim tokens, call submitnative!), with the channel lock folded in (a device's submits are serialized; ~24 us each). Keeps: the graph semaphore (serializes a graph), arena conditions (held across host functions), the lock-free inbox for finalizers only, the kernel lock. Removes: plan sync locks, per-resource locks and their id order, lockplans/lockresources/lockexpanded, the immutable-snapshot-and-check pattern for namers, readers and members (plain sets mutated under the lock), runend, table locks, Retry results. The prepare-outside/check-inside/Again pattern stays (allocation cannot happen under the lock). Consequence: contention between threads is per device, never across devices; the bookkeeping is far cheaper than the driver submit. Risk: a device-wide lock across `submitnative!` serializes submits; acceptable for one process (editor + DNN + RayMakie), and the channel lock can be split out later without changing semantics.
D2. HOST NODES mid-run staleness: WaitFor, between, runend, inhostfunction scan, heldforrun/blockedfrom. Under D1 most of it becomes a field read under the device lock and a condition wait outside it. Recommend keeping the semantics (a change a running plan cannot follow is applied after the run; another submitter waits; from a host function it throws) but implementing it with the device lock: no separate runend lock, no lock-free between flag.
D3. CAPABILITIES. `caps(dev)` has no kernel-feature facts: cooperative matrices (shapes, element types, scopes), subgroup size, fp16/bf16 arithmetic, Float64, 64-bit atomics, memory orderings, ray query in compute, mesh shaders. Candidates have `implements` and a region compiler but no `requires`. Recommend: (a) `caps(dev)` gains those facts; (b) a candidate declares `requires(c)` (a set of capability facts) and `select` filters by it; (c) a "kernel contract" section in api.md: what a kernel may use on every device type and what is gated (KernelInterface intrinsics for cooperative matrices and subgroup operations, with `KI.supports_*`); (d) library kernels (GEMM, attention, conv) are core candidates written against those intrinsics, with the device type contributing only vendor-library candidates.
D4. SELECTION TABLE MEASUREMENT (F8). When measurement runs, where the table lives, how it is invalidated (driver, kernel code). Recommend: a per-device table in the device object; an entry is measured on first use when `Graph(dev; autotune = true)` (name open) or by an explicit `tune!(dev, f, key)`; never implicitly inside run!; persisted nowhere in phase 6 (a scratch file is a later item). State it in the plan and api.md.
D5. BUILD STRATEGY (depends on the src audits): in-place phases 1-12 vs a fresh core and fresh backends against the suite with the old tree consulted only for driver facts.
D6. WEAK REFERENCES: `GraphDevice.graph::WeakRef`, `WeakPlan`, `WeakSet{BuildRecording}`, `Window.graph::WeakRef`, LRU list of weak refs. Each is a place where `nothing` must be handled on every read. Recommend: holds instead of weak refs where lifetime is already counted (a plan is retired explicitly: dependents and namers can hold it strongly and be removed at retirement, as `unregister!` already does), leaving weak refs only for the LRU list.
D7. The per-resource `Access` records keep "the latest read per channel" and the last write; with a device lock these stay as they are.

### Goal checks still open
G1. "Simple implementation": the pseudocode alone is 4000 lines with helpers undefined; a faithful implementation of core as written is likely 15-20k lines. D1/D2/D6 reduce it; the rest (pieces, windows, eviction, TLAS) is inherent to the goals.
G2. Eager path = one submission per launch at ~24 us (F29): GPUArrays' generic code (a broadcast chain on device arrays) pays that per kernel. Acceptable by design; say so in api.md 2.2.

## After the suite (all 42 areas read)

### Headline
S0. APIPHASE = 6 (helpers.jl): "the suite runs nothing before APIPHASE". Phases 1-5 of the in-place plan have NO executable new-API test; the only tests are the old tree the plan is deleting. ### Suite-vs-docs gaps (names the suite assumes that api.md does not define)
S1. Operations in a group: `mul!(loop, C, A, B)` (DECL-08), `copyto!(loop, dst, src)` (REP-12), `triu!(loop, x)` is a MethodError (REP-11). internals.jl section 2 says "how an operation reaches a group is open". S2. `visible!(tlas, r, flag)` (CO-06, TL-08, RM-11, resizing A): not in api.md 2.6. Add.
S3. S9. `Mantle.fft(z)` (EAGER-01) and `mul!` as library operations; `Image(dev, Float32, 16, 16)` + `clear!(dev, img, 1f0)` scalar clear value for a one-channel image; `Array(img)` returns a Matrix with first index x (pieces.jl); `copyto!(img, data)` same size, `copy!(img, data)` new size, `resize!(img, w, h)`; `Image(g, T, win)`.
